# Feature Specification: M6 Release Packaging

**Feature Branch**: `006-m6-release` (spec directory; work happens on the current branch)

**Created**: 2026-10-29

**Status**: Draft

**Input**: User description: "Milestone M6 from docs/spec.md: `cargo-packager` config, CI matrix
(macOS/Windows/Linux) building `.dmg`, NSIS `.exe`, `.deb`/AppImage on tag push; README with
screenshots; THIRD-PARTY notices (e.g. `cargo-about`). Done when a tag build produces 3 OS
artifacts and the human installs on at least one OS. Do not add requirements."

**Source of truth**: `docs/spec.md` §1 (License row; Slint license constrains the repo license;
`NOTICE`), §2 (`.github/workflows/ci.yml`), §7 (M6 row), §10 (no macOS signing or notarization;
document the Gatekeeper workaround in the README), and the existing `LICENSE` (GPL-3.0) and
`NOTICE` (Slint used under GPL-3.0; "Third-party dependency notices are generated at release time
(milestone M6)"). Details below that `docs/spec.md` leaves open are router decisions dated
2026-10-29 under the human's overnight delegation; none changes a rule, the schema, or the API.

## User Scenarios & Testing *(mandatory)*

The users are (a) a student who downloads the app for their operating system and installs it
without building from source, and (b) the maintainer who publishes a release by pushing a version
tag.

### User Story 1 - Maintainer cuts a release with one tag (Priority: P1)

The maintainer pushes a tag such as `v0.1.0`; CI builds installers for macOS, Windows, and Linux
and attaches them to a draft GitHub release for review.

**Why this priority**: It is the M6 done-when condition.

**Independent Test**: Push a test tag to the repository; the release workflow finishes green on all
three runners and the draft release holds a `.dmg`, an NSIS `.exe`, a `.deb`, and an `.AppImage`.

**Acceptance Scenarios**:

1. **Given** a pushed tag matching `v*`, **When** the release workflow runs, **Then** it builds on
   macOS, Windows, and Linux runners in a matrix and each job runs `cargo-packager` in release mode.
2. **Given** the jobs succeed, **Then** the macOS job yields a `.dmg`, the Windows job an NSIS
   setup `.exe`, and the Linux job a `.deb` and an `.AppImage`, all attached to one draft GitHub
   release named after the tag.
3. **Given** a normal push or pull request (no tag), **Then** the release workflow does not run;
   the existing CI checks still run unchanged.
4. **Given** the tag's version differs from the workspace version in `Cargo.toml`, **Then** the
   workflow fails before packaging with a message naming both versions.

---

### User Story 2 - Student installs the app (Priority: P1)

A student downloads the installer for their OS, installs it, and launches "Academic Planner" from
the usual place (Applications, Start menu, app launcher).

**Why this priority**: The second half of the done-when condition (human installs on one OS).

**Independent Test**: The human installs one artifact on their machine and the app opens with an
empty planner (or their existing data).

**Acceptance Scenarios**:

1. **Given** the `.dmg` on macOS, **When** the student drags the app to Applications and opens it
   using the README's Gatekeeper steps, **Then** the app window opens.
2. **Given** the NSIS installer on Windows, **When** run, **Then** the app is installed with a
   Start-menu entry and an uninstaller.
3. **Given** the `.deb` or `.AppImage` on Linux, **Then** the app installs (deb) or runs directly
   (AppImage, after `chmod +x`).
4. **Given** any install, **Then** the database lives in the per-user data folder (R24), never in
   the install folder.

---

### User Story 3 - README and third-party notices (Priority: P2)

The repository has a README explaining what the app does, how to install each artifact, how to
build from source, where the data lives, and the licenses; and every release carries the
third-party license notices of its Rust dependencies.

**Why this priority**: Required by §7 and by the GPL/third-party license terms, but it does not
block a working installer.

**Independent Test**: Open README.md on GitHub: it shows screenshots, install steps per OS,
including the macOS Gatekeeper workaround, and build steps; each installer contains a
third-party notices file.

**Acceptance Scenarios**:

1. **Given** README.md, **Then** it contains: a one-paragraph description; screenshots of the main
   pages; download and install steps for macOS (including the Gatekeeper workaround, §10),
   Windows, and Linux; build-from-source steps (`cargo run -p app`); where the database lives and
   the `ACADEMIC_PLANNER_DB` override (R24); backup/restore and CSV export in one paragraph; and
   the license (GPL-3.0, Slint under GPL-3.0, link to NOTICE and third-party notices).
2. **Given** a release build, **Then** a third-party notices file generated by `cargo-about` from
   `Cargo.lock` is bundled in every installer and attached to the release.
3. **Given** `NOTICE`, **Then** it points to the generated third-party notices instead of saying
   they will be generated in M6.

---

### Edge Cases

- **Unsigned macOS app**: Gatekeeper blocks the first launch; README gives the right-click → Open
  (or System Settings → Privacy & Security → Open Anyway) steps (§10). No signing or notarization.
- **Unsigned Windows installer**: SmartScreen may warn; README says "More info → Run anyway".
- **Linux AppImage portability**: build on the oldest supported Ubuntu runner available so the
  AppImage runs on common current distributions.
- **License not allowed by policy**: if `cargo-about` finds a dependency license not in the
  accepted list, the release job fails and names the crate.
- **Screenshots**: README screenshots need the app on screen; if no human is available when the
  README is written, the README references image files under `docs/screenshots/` and the capture
  is listed as a human task.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** (§7): A `cargo-packager` configuration for the app (product name "Academic
  Planner", identifier, version from the workspace, license, the release binary
  `academic-planner`) producing `dmg` on macOS, `nsis` on Windows, and `deb` plus `appimage` on
  Linux.
- **FR-002** (§7, router decision): A release workflow `.github/workflows/release.yml` triggered
  only by pushed tags matching `v*`, with a macOS, Windows, and Linux matrix, which builds in
  release mode, packages with `cargo-packager`, and attaches all artifacts to one draft GitHub
  release for the tag.
- **FR-003** (router decision): The release workflow checks that the tag equals `v` + workspace
  version before packaging.
- **FR-004** (§7, `NOTICE`): `cargo-about` configuration (accepted licenses + template) that
  generates a third-party notices file from `Cargo.lock`; the release workflow generates it and
  bundles it in every installer and attaches it to the release; `NOTICE` is updated to point to it.
- **FR-005** (§7, §10): `README.md` with the contents listed in User Story 3, scenario 1.
- **FR-006** (§1): The existing CI workflow (fmt, clippy, test, theme grep, DESIGN.md lint) is
  unchanged in behavior; the gate still passes.
- **FR-007** (§7): The human pushes a tag, confirms the three OS artifacts, and installs one; this
  is a human step (pushing a tag is outward-facing and is not done by the agents).

### Key Entities

- **Release artifacts**: `.dmg`, NSIS `.exe`, `.deb`, `.AppImage`, and the third-party notices
  file, per tag.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: One tag push produces installers for all three operating systems with no manual
  build steps.
- **SC-002**: A student installs and opens the app on at least one OS by following the README
  alone.
- **SC-003**: Every installer includes the third-party notices for 100% of its Rust dependencies.
- **SC-004**: The gate passes and the regular CI is unaffected.

## Assumptions

- The first release version is the current workspace version `0.1.0` (tag `v0.1.0`).
- The release is created as a draft so the maintainer reviews it before publishing.
- No app icon is specified in `docs/spec.md` or `DESIGN.md`. `cargo-packager` has no default icon
  and its AppImage step requires a square PNG, so a placeholder icon (a plain square in DESIGN.md
  `primary`) is used until the human supplies one (planner finding 2026-10-29, research R-6).
- `cargo-packager` and `cargo-about` are installed in CI with pinned versions.
- Local verification is limited to the host OS (macOS): building the `.dmg` locally proves the
  packager config; Windows and Linux packaging are verified by the tag build.
